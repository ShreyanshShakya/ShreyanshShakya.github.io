# Weather Prediction: From Thousands of Cities to a Deployable Forecasting System

Weather forecasting is a good example of a problem where the machine-learning model is only one part of the engineering challenge. This project focused on building a city-specific forecasting workflow that could train models across thousands of Indian cities and expose the resulting models through a live prediction interface.

## The Problem

The goal was to predict the **next day's average temperature** for individual cities. Instead of relying on a single model for every location, the project trains separate XGBoost models for individual city histories.

The challenge quickly became one of scale: the dataset is large, the number of city models is large, and the training process needs to be repeatable and resumable.

## Dataset

The project uses the **Indian 5000 Cities Weather Data** dataset from Kaggle. The repository describes approximately **90 GB of historical weather data covering 6,000+ Indian cities**. A verification run in the training pipeline found **4,408 city datasets** in the available input data.

The system works with historical observations and transforms them into time-based and lag features before training the city models.

## Architecture: The GitHub README Design

The final system follows the architecture documented in the project repository:

```text
[Kaggle Dataset]
        ↓
[Kaggle Training Pipeline]
        ↓
[Hugging Face Model Hub]
        ↓
[FastAPI Server]
        ↓
[Gradio UI]
```

### 1. Kaggle Dataset

The historical weather dataset is mounted through Kaggle. This avoids treating the entire dataset as an ordinary local download and makes the large input available to the training environment.

### 2. Kaggle Training Pipeline

The training workflow discovers city CSV files, processes each city's history, creates features, trains an XGBoost regressor, evaluates it with mean absolute error, and prepares the resulting artifacts for upload.

The repository also contains verification logic that compares cities found in the dataset with model folders already present in the model registry. This makes the large training job resumable instead of requiring every city to be retrained from scratch.

### 3. Hugging Face Model Hub

Trained city models are uploaded to a centralized Hugging Face Model Hub repository. The training notebook stores the XGBoost model as `model.json` together with metadata containing the city name, validation MAE, and feature list.

### 4. FastAPI Server

The serving layer is a Dockerized FastAPI application. The documented design dynamically loads models when required and caches them so that frequently requested models do not need to be loaded repeatedly.

### 5. Gradio UI

A Gradio interface provides the user-facing forecasting experience and communicates with the prediction service.

## Feature Engineering

The training pipeline uses a deliberately simple and repeatable feature-engineering process. For each city it:

- Converts the date column into a datetime index
- Adds month, day of year, day of week, and year
- Adds temperature lag features for the previous one and two observations
- Adds a previous precipitation feature when precipitation is available
- Calculates a seven-observation rolling mean of temperature
- Removes incomplete rows before training

The training workflow then selects numeric features and performs a chronological 80/20 train-test split without shuffling.

## Training the City Models

The single-city training workflow uses an **XGBoost Regressor** configured with:

```text
n_estimators = 500
learning_rate = 0.05
max_depth = 6
```

For each city, the pipeline trains the model, calculates mean absolute error, saves the model as JSON, writes metadata, and uploads the artifacts to the Hugging Face model repository.

The multi-city pipeline is configured to process up to 5,000 cities. The verification workflow recorded 4,408 cities in the dataset and checks which corresponding model folders have already been uploaded.

## Engineering Challenges

### Working with a Large Dataset

The project uses Kaggle's mounted storage for the large weather dataset. This makes it possible to process the data in the environment where the training pipeline runs.

### Managing Thousands of Models

A city-specific modeling strategy produces a large number of independent model artifacts. A centralized model repository and verification process make those artifacts easier to organize and track.

### Making Training Resumable

The training workflow checks which city models have already been uploaded and identifies missing models. This is important because a failure or interruption should not force the entire multi-city job to start again.

### Serving Many Models

A conventional application that loads every city model at startup would not be a practical design for a large model collection. The documented API architecture instead uses on-demand model loading and caching.

## API

The deployed architecture exposes a `/predict` endpoint. The repository README specifies that a request should provide at least seven days of historical weather data and returns the predicted next-day average temperature.

## What I Learned

1. **Model training is only one part of an ML system.** Once the number of models becomes large, storage, verification, and serving become important engineering problems.
2. **Repeatability matters at scale.** A workflow that works for one city needs automation before it can reliably handle thousands.
3. **Model management becomes part of the application.** A centralized registry and a way to identify missing models are essential when every city has its own artifact.
4. **Serving architecture has to account for model count.** On-demand loading and caching provide a practical way to work with many models.
5. **Simple feature engineering can still be useful.** Consistent temporal and lag features provide a reproducible baseline across cities.

## Future Work

Possible extensions include experimenting with additional forecasting models, improving feature engineering, adding stronger model monitoring, and further automating retraining and deployment.
